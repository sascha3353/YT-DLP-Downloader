# Project Instructions

## Conventions
- `APP_VERSION` in `ytdl/__init__.py` is bumped **only at an explicit git commit** – not per working-tree change. Between commits, leave the version at the value it had at the last commit (or the pre-existing uncommitted value).
- `CHANGELOG.md` is the **canonical** user-facing history; the GitHub release notes are written from it and link back to it. Keep the two from drifting: the release commit that bumps `APP_VERSION` for a shipped version is also the commit that adds that version's entry to `CHANGELOG.md` (an `## Unreleased` heading holds in-progress work). Entries describe what a *user* observes, not the implementation, and are grouped per version rather than generated from `git log` – the commit history already has the internals, and a generated list buries the few entries that matter. Three releases change files already on disk (1.3.10 bare subtitle naming, 1.3.13/1.4.0 the layout rewrite, 1.4.0 the SponsorBlock retiming removal); those carry a **⚠ Changed on disk** marker. Because `APP_VERSION` is bumped per commit, several versions shipped without a published GitHub Release (1.3.7–1.3.15, and 1.1.25 was skipped entirely) – a version entry without a release link means "committed and shipped, never published", not "missing".

## How to Investigate
- `main.py` – the thin launcher at the **repo root**: parses argv, starts the app, and re-exports the public names of `ytdl.app` so `main.detect_site` / `main.YTDLPDownloaderGUI` etc. remain the single import surface for tests and tooling.
- `ytdl/` – the application package: GUI class in `ytdl/app.py`, pure logic in the sibling modules (see Repository layout).
- `requirements.txt` – Python dependencies (PyQt6, requests, pyobjc-framework-Cocoa). The external binaries (`yt-dlp`, `ffmpeg`, `deno`) are only listed as comments – install them via Homebrew or pip, not via this file.
- No CI workflow exists (no `.github/`, no `ci.yml` / `pre-commit.yml`). Build and test are manual, see below. Lint config lives in `.pylintrc` (pylint 4.x; run `python3 -m pylint ytdl main.py` once pylint is installed — that is the source of truth). The VS Code `ms-python.pylint` extension does **not** reliably find `.pylintrc` on its own, so `.vscode/settings.json` passes `--rcfile=${workspaceFolder}/.pylintrc` explicitly; without it the editor ignores the `disable=` list and reports every function as missing-function-docstring. Ignore `temp/`, `scratch/`, `archive/` and `build/` in the editor as well – `.pylintrc` already excludes them. It disables only introspection noise for compiled Qt/PyObjC extension modules and this codebase's documented style choices (docstrings per function, line length, f-string logging, broad excepts at the UI/network boundary, too-many-* in GUI handlers); the check for each disabled message is listed with its reason in the file, so they can be re-enabled selectively.
- Runtime preferences are NOT the repo's `preferences.json` – the app reads and writes `~/Library/Application Support/YT-DLP Downloader/preferences.json` (see `PREFERENCES_DIR` in `ytdl/app.py`, edited via the in-app dialog). Keys: `channel_name_map`, `strip_bracketed_soundcues`, `cookies_from_browser` and `cookies_from_browser_enabled` (the browser cookies are an on/off switch plus the browser name), and `show_fetchinfo_command`. The repo-root `preferences.json` is only a reference sample.

## Repository layout (flat at the root, plus `assets/` and the `ytdl/` package)
- `main.py` – thin launcher + facade; run from the repo root with `python3 main.py` (works from any cwd). It parses argv, calls `configure_logging()` (see below), starts the app, and re-exports the public names of `ytdl.app` so `main.detect_site` / `main.YTDLPDownloaderGUI` etc. remain the single import surface for tests and tooling.
- `ytdl/app.py` – class assembly (`YTDLPDownloaderGUI` inherits the per-concern mixins), `__init__` shared-state init, URL/clipboard handlers, output-panel helpers, dock methods, `APP_VERSION` re-export.
- `ytdl/config.py` – app-wide constants (`DEFAULT_OUTPUT_DIR`, `TITLE_FETCH_DELAY_MS`).
- `ytdl/preferences.py` – preferences file path/loading and in-memory state (`preferences`, `CHANNEL_NAME_MAP`); mutate via `apply_preferences()` and read live values through the module. Owns the `strip_bracketed_soundcues` preference (default **true**): it gates `_strip_nonspoken_brackets()` in `resync_subtitles`, which removes `[laughter]` / `[snorts]` / `[musik]`-style tokens. The reader takes an optional dict for testing and falls back to its default on an absent or unusable value, so a malformed file cannot silently switch behaviour — and it rejects a non-`bool`, because `bool` is a subclass of `int`. It also owns the **browser cookies**: `cookies_from_browser_enabled` (the on/off switch, default **false**) and `cookies_from_browser` (the browser name, e.g. `firefox` or `firefox:1abc2def.default-release`). `cookie_browser()` is the single place that decides whether yt-dlp gets `--cookies-from-browser` — the switch must be on **and** a valid browser name must be set; both the info fetch (`ytdl/info_fetch.py`) and the download command (`ytdl/command.py`) call it. An absent `cookies_from_browser_enabled` key migrates to *on* when a browser name is configured, so an existing install keeps its cookies. `show_fetchinfo_command` has a reader of its own (`show_fetchinfo_command()`, default **off**) instead of the raw `.get()` the info fetch used before. It also owns the **help texts** for the Preferences dialog: one `TOOLTIP_*` constant per preference key (`TOOLTIP_COOKIES_FROM_BROWSER_ENABLED`, `TOOLTIP_COOKIES_FROM_BROWSER`, `TOOLTIP_STRIP_BRACKETED_SOUNDCUES`, `TOOLTIP_SHOW_FETCHINFO_COMMAND`, `TOOLTIP_CHANNEL_NAME_MAP_EDITOR`), shown as the tooltip of the widget that owns the key (so the dialog needs no separate explanations section). Each text names the key, its accepted values and its default. They live here rather than in the dialog so they can be checked without Qt. `subtitle_words_per_cue` and the sentence-aware `layout_cues()` stage it drove were removed in 1.4.3; a leftover key in an existing `preferences.json` is simply ignored.
- `ytdl/info_fetch.py` – `InfoFetchMixin`: video-info fetch (yt-dlp subprocess), parsing, description summary, SponsorBlock API. Also exports `apply_episode_rules(channel, title) -> (episode_code, clean_title)` and `_EPISODE_RULES` — a pure, Qt-free function that handles per-channel episode-number extraction (PowerfulJRE, Shawn Ryan Show, Lex Fridman, PBD Podcast); adding a new channel is a one-line table entry. `build_title_with_prefix(prefix, title)` is the matching pure helper that assembles the display/download title: it sanitizes and prepends `"<prefix> - "` only when a prefix exists, so a video with no usable `upload_date` no longer yields `" - Title"` (an orphaned dash that `sanitize_title()` preserves, and that became the on-disk folder/file name). The date parse sets the prefix to `""` on `ValueError` — an unparseable date is reported in the log but never used as a prefix.
- `ytdl/download.py` – `DownloadMixin`: download orchestration (start/build command/run), yt-dlp output/progress parsing, file metadata, NFO/EDL creation. Also the `.edl only` media type (`EDL_ONLY_MEDIA_TYPE`, `start_edl_only`/`run_edl_only`/`create_edl_only`) and the SponsorBlock API/category helpers (`fetch_sponsorblock_segments`, `to_ui_category`, `SB_ALL_API_CATEGORIES`, `write_edl`). `start_download()` and `build_command()` must BOTH store the sanitized basename in `video_state["base_filename"]` (`update_video_state` maps `title` → `base_filename`): the first creates the output directory, the second builds the yt-dlp `-o` template, and a mismatch means the media lands in a subpath of the created folder while the existence checks/`get_full_path()` look elsewhere. A title that sanitizes to an empty string (e.g. `".."`, `"!??"` — note `/` becomes `-`, so a slash-only title is *not* empty) falls back to `"downloaded_video"`, and an empty channel name falls back to `"Unknown Channel"`, so neither collapses the path to the output root.
- `ytdl/subtitles.py` – `SubtitleMixin`: subtitle selection/file mapping, and `resync_subtitles()` (parse, then hand off to the layout stage; timestamps are never retimed — see "SponsorBlock handling"). It also owns the **on-disk subtitle naming policy**: a video whose only subtitle track is stored as `<title>.srt` (no language code) — see "Subtitle file naming" below.
- `ytdl/subtitle_layout.py` – the display-layout stage, pure (no Qt, no filesystem). One function, `rolling_cues()`: it groups the ASR's own windows in twos — `ROLLING_WINDOWS_PER_CUE` consecutive windows per cue, one window per line, nothing repeated or re-cut — and starts each cue at its first window's exact timestamp, so two caption lines show at once exactly as the YouTube player shows them. See "Subtitle display layout" below.
- `ytdl/ui_build.py` – `UiBuildMixin`: `init_ui` widget construction, styling, menus, dialogs, UI enable state.
- `ytdl/preferences_dialog.py` – `PreferencesDialogMixin`: the preferences editor dialog. It shows a **form** for the four switches above the raw JSON editor: a `cookies_from_browser` checkbox + a browser text field (the latter enabled only while the checkbox is on), plus `strip_bracketed_soundcues` and `show_fetchinfo_command` as plain checkboxes. The form has no group frame or title: the cookie checkbox and the browser field sit on one line directly in the dialog (the field flat — no padding, no rounded corners, the pane's regular font size). The **JSON editor holds only `channel_name_map`** — the switches live in the form, so the file the user edits by hand stays small. The form is authoritative for its four keys (`_FORM_OWNED_KEYS`): a value typed into the JSON editor for one of them is ignored on save. The JSON editor is authoritative for `channel_name_map` — an editor that drops the key means an empty map, not "keep the old one". Any *other* key already in `preferences.json` is **carried over** on save (`_read_preferences_file()`), so a hand-added entry is never dropped; a form-owned key whose widget was not supplied keeps its value from the file rather than losing it. Each switch has an `objectName` equal to its JSON key, so the headless check in `temp/check_prefs_dialog.py` can find it. **There is no explanations section any more**: the help text for each key is the **tooltip of the widget that owns it**, and the texts live in `ytdl/preferences.py` (`TOOLTIP_*` constants) so they can be checked without Qt. The dialog has **no path label** at the top either — the edited file's path is in the JSON editor's tooltip, so the dialog opens straight on the settings. Both file reads are **total**: they catch `UnicodeError` (a file that is not valid UTF-8) as well as `OSError`, so a corrupted or hand-edited file cannot stop the dialog from opening or block a save — it is treated as empty and the save replaces it with a valid file.
- `ytdl/sites.py` – site profiles (`SUPPORTED_SITES`, `DEFAULT_SITE`, `SUPPORTED_SITES_LABEL`), ID regexes, `detect_site()`, `is_known_site()` (strict domain gate), `is_channel_url()` (channel/playlist gate), `site_*()` profile helpers, `is_plausible_url()`, `normalize_url()`.
- `ytdl/progress.py` – yt-dlp output parsing tables (`RE_*`, `SUBTITLE_EXTENSIONS`) and `DownloadProgressManager`.
- `ytdl/widgets.py` – small Qt support classes (`SignalEmitter`, `SponsorBlockBar`, `BusySpinner`, `CustomTextEdit`) and the `SB_*` category constants.

- `ytdl/utils.py` – `resource_path()` (dev branch resolves the repo ROOT, one level above the package), `get_log_dir()`, `find_binary()`, `sanitize_title()`, `canonical_subtitle_lang()` / `SUBTITLE_LANG_ALIASES` (site subtitle key → UI code, e.g. `deu`→`de`), duration/filesize/SRT-time formatters, and `format_subtitle_stats()` (the `📊` layout-summary line).

## Execution scaffold
- Install dependencies: `pip install -r requirements.txt`.
- Run GUI: `python3 main.py` (cwd-independent; `resource_path()` uses `sys._MEIPASS` or `__file__`).
- Test flag: `python3 main.py --simulate-download-error` (makes downloads raise immediately).
- External binaries `yt-dlp`, `ffmpeg`, `deno` are typically installed via Homebrew (not pip); `find_binary()` also detects a pip-installed copy in the launching Python's bin.
- Packaging: `./build-macos.sh` → `dist/YT-DLP Downloader.app`; a bare single-file binary via `pyinstaller --onefile main.py` → `dist/app`.

## Execution flow
- GUI triggers `fetch_video_info` → `start_download`.
- **Logging is configured by the launcher, not by the library.** `main.configure_logging()` (called only from the `__main__` block) sets up the root logger's `FileHandler` on `~/Library/Logs/YT-DLP Downloader/app.log` plus stderr. `ytdl/app.py` deliberately does *not* call `logging.basicConfig()`: it is imported by `main`, by all 30 `temp/test_*.py` modules and by the replay helpers, so configuring at import time meant **merely running the tests appended synthetic entries to the user's live log** (measured: 89 lines from one 35-test module). Do not move it back into `ytdl.app`; `temp/test_log_isolation.py` fails if a library ever configures logging on import again.
- `fetch_video_info()` pre-checks the URL syntactically (`is_plausible_url()`, also used by the clipboard paste/startup handler) so garbage like "nonsense" never reaches the yt-dlp subprocess; naked 11-char YouTube IDs and schemeless known-site tokens still pass because `normalize_url()` canonicalizes them first. The hostname must be well-formed (dot-separated labels of letters/digits/hyphens) — Python's `urlparse` is lenient and would otherwise accept clipboard text like "YT-DLP Downloader 1.1.25" as a "URL".
- The domain gate is strict: `is_known_site()` (reached through `url_rejection_reason()`) requires the hostname to match a `SUPPORTED_SITES` profile, so unsupported sites (e.g. google.com, vimeo.com) are rejected with "Unsupported site — supported: …" instead of being handed to yt-dlp's generic extractor. `detect_site()` keeps its YouTube fallback for behavior flags; to accept another site, add a profile.
- Info-fetch failures are surfaced in the output panel: `get_video_info()` dumps yt-dlp's captured stdout/stderr via `_dump_ytdlp_error_output()` (headline includes the exit code; a timeout dumps the partial output captured before the kill). Previously stderr was swallowed, so 403/sign-in errors made the app look like it silently stopped.
- Progress reported via `DownloadProgressManager` and `SignalEmitter` signals.

## Multi-site support (YouTube + Rumble + Odysee + ARD Mediathek + ZDF Mediathek + RTVE Play)
- `SUPPORTED_SITES` (top of `ytdl/sites.py`) holds per-site profiles: `domains`, `id_regex`, `sponsorblock`, `js_runtime`, `resync_auto_subs`, `supports_subtitles`, `always_extract_audio`, `channel_url_regex`, `info_timeout`. `detect_site()` matches the hostname; unknown domains fall back to `DEFAULT_SITE` (YouTube) for behavior flags, while `is_known_site()` is the strict domain gate (unknown domains are rejected before yt-dlp runs) and `is_channel_url()` rejects channel/playlist pages per site. New profile flags must default to the historical behavior for unknown sites.
- Channel/playlist patterns mirror yt-dlp's own extractors: ARD rejects the `sendung`/`serie`/`sammlung` collections (`ARDMediathekCollectionIE`), while ZDF uses an inverse heuristic because `ZDFChannelIE` is a catch-all playlist for every `zdf.de` path — only `/video/`, `/play/` and legacy `<slug>.html` single videos pass (path-anchored in the profile), so a ZDF show page like `/magazine/heute-journal-104` (resolves to a 30-entry playlist) is rejected.
- Website availability ≠ yt-dlp availability: the ARD/ZDF web player's "not available" (geo/rights) is a separate client-side check — yt-dlp only fails when the player API returns **no** formats, and ARD's extractor then raises (`_geoblocked` → "This video is not available due to geoblocking"; `"fsk"` in the page → "only available after 20:00"). Observed live: a video the browser reports as unavailable on ARD downloaded fine through the app; when extraction genuinely fails, the reason lands in the output-panel dump.
- Input gating lives in one place: `YTDLPDownloaderGUI.url_rejection_reason()` (plausible URL → known site → not a channel URL); `fetch_video_info()` and the clipboard paste path both use it.
- Info-fetch budget is per site: `site_info_timeout()` returns the profile's `info_timeout` or `config.INFO_FETCH_TIMEOUT_SECONDS` (15s). Odysee sets 90s because the LBRY API `resolve` call routinely takes ~40s (measured; short claim ids like `:d` are slow) and the old hardcoded 15s killed it mid-resolve.
- Long info fetches report progress: `get_video_info()` runs through `_run_info_command()`, which starts a daemon monitor (`_info_wait_monitor`) that emits "⏳ Still fetching video info (Ns) — <hint>…" after `config.INFO_FETCH_HINT_AFTER_SECONDS` (10s) and every `INFO_FETCH_HINT_EVERY_SECONDS` (20s) while yt-dlp is still resolving. The hint text is per site (`slow_hint`, e.g. Odysee's LBRY API); sites without one get "the site is responding slowly".
- Site-gated behaviors: SponsorBlock (the API query in `check_sponsorblock()`, `--sponsorblock-mark`, the `.edl only` writer, and the download path's EDL sidecar `create_edl_file()` — all four behind one helper, `site_supports_sponsorblock()` in `ytdl/sites.py`, YouTube-only), `--js-runtimes deno` (needed by YouTube's JS sig/nsig challenges, skipped for Rumble/Odysee/ARD/ZDF/RTVE Play), auto-subtitle resync/2-line merge (needed for YouTube's choppy ASR cues; Rumble subs arrive pre-formatted and are kept as-is; Odysee has no subs at all), video format selector uses `bestvideo*` (not strict `bestvideo`) so muxed HLS formats with unknown codecs (Rumble, Odysee) are eligible – strict `bestvideo` would degrade Rumble downloads to the tiny video-only timeline strip. `always_extract_audio` forces `-x` for sites without audio-only streams (Odysee and ZDF — every ZDF format is muxed), otherwise "Best" audio would save the muxed source video file.
- **All-defaults optimization**: when Quality=Best, Video=Best, Audio=Best (the defaults), the download uses `-f best` (single muxed stream, no merge). This typically yields ≤720p on YouTube because 1080p+ are DASH (separate streams). Any non-"best" setting uses the full `bestvideo*[filters]+bestaudio/best` selector for full resolution.
- Sites without subtitle support (`supports_subtitles: False`, e.g. Odysee — the LBRY extractor exposes no tracks) print "Subtitles: Not available on <label>" instead of the generic "(none)" line during info fetch.
- Embedded broadcast captions (EIA-608 in H.264 SEI T.35 NALs, carried by Rumble's HLS streams; IINA surfaces them as a hidden "eia_608" subtitle track) are stripped **only for sites whose profile sets `strip_embedded_cc` (Rumble alone)** via `--postprocessor-args Merger/FixupM3u8:-bsf:v filter_units=remove_types=6` in `build_command()`. The filter is site-gated because unit type numbering is codec-specific: in AV1 an OBU of type 6 is a Frame OBU, so applying the filter unconditionally deleted picture data and corrupted AV1 downloads (observed on YouTube, where `best` picks AV1). The app's own SRT files are the intended subtitles.
- Subtitle key shapes differ per site: yt-dlp matches `--sub-langs` entries as regexes with `fullmatch` against the site's subtitle keys (YouTube `en`/`a.en`, Rumble `en-auto` with generated subs in `subtitles`, not `automatic_captions`). `_subtitle_lang_patterns()` therefore requests every known key shape, and `_find_downloaded_subtitles()` + `_normalize_subtitle_names()` map site-named files (`<base>.en-auto.srt`) back to the canonical `<base>.en.srt` **before** post-processing, so resync overwrites in place instead of leaving duplicates. German public-media sites (ARD/ZDF) key their tracks by ISO 639-2 (`deu`); `canonical_subtitle_lang()` (`ytdl/utils.py`) maps those keys onto the UI's 639-1 codes at all three touch points (the availability match in `info_fetch.py`, the `--sub-langs` patterns and downloaded-file matching), so the German checkbox shows availability and files end up renamed `<base>.de.srt` (or plain `<base>.srt` when it is the video's only subtitle — see "Subtitle file naming").

- **`real` vs `auto` comes from the info fetch, not from the filename.** `_subtitle_needs_resync()` skips the 2-line merge for `real` (manual) tracks, so classifying a track wrongly silently stores the raw captions instead. The filename can only prove "auto" when the *site* named the key that way (Rumble's `en-auto`): current yt-dlp merges `--write-subs` and `--write-auto-subs` into one language namespace (a manual track wins the slot, `YoutubeDL.process_subtitles`) and writes YouTube's automatic captions as plain `<title>.en.srt` — the `a.` prefix is never produced (verified against yt-dlp 2026.09.16: `[info] Writing video subtitles to: …/Title.en.srt`). `_find_downloaded_subtitles()` therefore resolves an unmarked name through `video_state["available_subtitles"]` (`"auto"` when the site offers no manual track for that language, see `info_fetch.py`); without an info fetch the name is the only evidence, so it stays `real`. This is what the pre-multisite code did (`available_info.get(lang, "real")`); the filename-only version in `_find_downloaded_subtitles()` disabled the merge for *every* YouTube ASR video, and the raw rolling cues then render as stacked lines in a player (newest cue above the previous one) because they overlap.
- **Restore point before the subtitle-layout refactor: tag `subtitle-layout-baseline` (v1.3.12).** That commit is the last state whose output was verified byte-for-byte. It is now historical only: v1.3.13 replaced the three heuristic passes with the sentence-aware stage, and **1.4.2 replaced that with the paired-window layout**, so nothing on `main` reproduces the baseline file any more. The tag is kept for archaeology — to see what the pre-refactor output looked like — not as a rollback target, because rolling back would also undo the multisite and pace work built on top. The byte-comparison that was possible against `6cc6799` is not repeatable.
- **Restore-point oracle.** The concatenated word stream of input and output is identical (verified on a real 87-minute ASR capture, 17271 → 17271 words). The pipeline is text-lossless; only segmentation and timing are ever at stake. Only two steps can discard a cue — the parse step's `no_text_cues` (blocks left with nothing but `[musik]`-style artifacts) and the 0.15 s floor — and both are counted in the summary line, so the numbers reconcile with the cue count in the file on disk. The final overlap guard is **not** a third one: see below.

## SponsorBlock handling
- **We mark, we never cut.** `build_command()` passes `--sponsorblock-mark all` (NOT `--sponsorblock-remove`), so the downloaded media still contains everything; `create_edl_file()` writes an `.edl` and the player jumps the marked ranges during playback. Earlier versions cut the video, and EDL turned out to work better, so cutting is not coming back. `create_edl_file()` and `create_nfo_file()` are also called in the failure path via `_try_create_sidecar_files()` — yt-dlp writes `.info.json` before downloading, so metadata is available even when the media download fails. **The EDL write is site-gated**: `create_edl_file()` checks `site_supports_sponsorblock()` before touching the `.info.json` and prints one "… — skipping EDL" line otherwise, because `--sponsorblock-mark` never ran for a non-YouTube site either, so its `.info.json` can never contain `sponsorblock_chapters` — without the gate every ARD/ZDF/Rumble/Odysee download printed "Selected SB categories / No sponsorblock_chapters / No segments to skip", contradicting the info fetch's "SponsorBlock: Not available for this site" line (reported from a real ARD download; the NFO sidecar is *not* gated — it describes the episode, not SponsorBlock).
- **The subtitles are deliberately NOT retimed.** They stay in the video file's own timeline, which is what an EDL-skipping player expects: it looks subtitles up by current media time, and after a jump that is still the *original* time. Retiming them into an edited timeline - what this app used to do, back when it physically cut the videos - makes every subtitle after a cut run early by the cumulative removed duration.
- **Why cutting was abandoned: keyframes.** A video can only be cut cleanly at a keyframe, and SponsorBlock segment boundaries fall wherever they fall - mid-GOP. Cutting there means snapping to the nearest keyframe (so the cut is not where it was asked to be), or re-encoding the whole file. The EDL route avoids both: the media file is untouched and the *player* jumps, so there is no keyframe constraint, no re-encode and no quality loss. The SponsorBlock time-map code that served the cutting workflow (`_calculate_time_adjustment`, `_build_time_map`, `_adjust_timestamp_with_map`, and the `removed_segments` parameters) has been removed along with it, so subtitles cannot be retimed by accident.
- Visual bar defined in `SponsorBlockBar`.
- Category colors in `SB_CATEGORY_COLORS`, mapping in `SB_API_MAP`.
- **The `.edl only` media type** (a **checkbox** in the Type group — `self.edl_checkbox` in `ui_build.py`; the Type group is four independent checkboxes, `video_checkbox` / `audio_checkbox` / `subtitles_checkbox` / `edl_checkbox`, while `RADIO_GROUP_CONFIGS` in `ui_build.py` still holds the Quality/Video/Audio/Container *radio* groups; value `EDL_ONLY_MEDIA_TYPE` = `"edl_only"` in `download.py`): writes `<title>.edl` from SponsorBlock data and downloads **nothing** — for media already on disk. `start_download()` branches on it right after the shared prelude (title gate, directory creation, `update_video_state`) and **before** `build_command()`, so no yt-dlp process is ever spawned; the worker is `run_edl_only()` → `create_edl_only()`, which prefers `sb_bar.segments` (already fetched for the bar during the info fetch — zero extra HTTP normally) and falls back to `fetch_sponsorblock_segments()`. Verdicts on the Download button: "EDL Created ✅" / "No EDL Written" / "EDL Error 🚨"; the Cancel button is never shown (there is no process to cancel). The prototype CLI it was grown from is `temp/sponsorblock_standalone.py`.
- **EDL naming never runs `splitext()` over the title.** `write_edl(edl_path, segments)` takes the **final** `.edl` path, and `create_edl_only()` appends `".edl"` to the extensionless `base_filename` — because `splitext("Lecture 1.5")` would eat the title suffix and write `Lecture 1.edl` next to `Lecture 1.5.mp4`, where no player would find it. `create_edl_file()` (the download path) still splits a real *media* path, which is correct there.
- **Two category sets, one UI vocabulary.** `SB_ALL_API_CATEGORIES` (`download.py`) is what the app's own `getSegments` request asks for — it feeds both the visual bar and the `.edl only` fallback — so it must contain every category a checkbox can select, including upstream `"hook"` (yt-dlp PR #14845; the Hook checkbox): a category missing from the request is never returned by the API, and the checkbox then matches nothing. `--sponsorblock-mark all` covers the download path through yt-dlp's own category set. API → UI naming goes through `SB_API_MAP` / `to_ui_category()` (`outro`→`ending`, `filler`→`tangents`, `poi_highlight`→`highlight`); `"hook"` passes through unrenamed on purpose.
- Use `self.sb_bar.set_segments(segments, duration)` to update.
- The lookup is **enrichment, not metadata**: `get_video_info()` emits `title_fetch_complete` (which re-enables the UI) *before* calling `check_sponsorblock()`, and only `check_sponsorblock()` → `_fetch_sponsorblock_segments()` touch the network, on their own daemon thread. It used to run inline before the emit, so a failing API (3 attempts × 15s + two 2s sleeps ≈ 49s) held the Download/Info buttons disabled.
- `check_sponsorblock()` keeps the *local* gate synchronous (site profile flag, extracted video id) so its log line keeps its place in the output panel; only the HTTP request is deferred. It takes an explicit `video_id` / `site` / `duration_sec` snapshot rather than reading `video_state` later, because the lookup thread would otherwise race a newer URL.
- One request on `SPONSORBLOCK_TIMEOUT_SECONDS` (config, 4s); no retry loop and no `time.sleep`. A SponsorBlock outage is reported in the output panel but never sets `error_status["error"]`.
- `_emit_description_summary()` is called from `get_video_info()` directly, not from inside the SponsorBlock path, so the summary no longer rides on that network call.

## Shell command limits (agent tooling)
**Cline's terminal setting should be `background exec`.** With the VS-terminal backend, input over roughly a kilobyte was corrupted: the command came back echoed two or three times, interleaved, and the process never started. Measured (each attempt discarded, nothing applied):

| command | input | "vs terminal" |
|---|---|---|
| 1 line | ~50 B | ok |
| 3 lines, no heredoc | ~90 B | ok |
| 1 line | ~470 B | ok |
| heredoc, 26 lines | ~80 B | ok |
| heredoc, 26 lines | ~1700 B | **broken** (echoed twice, never ran) |
| heredoc, 50 lines | ~2900 B | **broken** (a `git add` in the same batch silently did not run) |

It was **total size, not line count** — a 26-line heredoc of 80 B is fine, and heredocs were never the problem. With `background exec` the same payloads run correctly (verified up to ~4 KB), so the size limit is no longer a constraint; the rule below is a cheap habit, not a necessity.

Two failure properties that outlive the setting, because both cost time when unnoticed:
- **A corrupted command changes nothing** — the process never starts, and commands *after it in the same batch* silently never run (a `git add` went missing that way). After a failure, check `git status` or re-run a small probe instead of retrying the same payload.
- **Captured output can be polluted** (a stray `%` from the shell's progress indicator), so pipe long output through `grep`/`tail` and parse that, not the raw buffer.

House rules:
- Keep shell commands to a single short line. Write file *content* with the editor tool (chunked if needed — it rejects payloads over 6000 chars) and let the shell only **run** it: `python3 temp/script.py`, `git commit -F /tmp/msg.txt`. Inline content is fragile for ordinary reasons too (quoting/escaping, shell history).
- Throwaway scripts go to `/tmp`, written with the editor rather than piped in.

## Dock tile
- The overlay's overall fraction (`DownloadProgressManager.get_combined_fraction()`) is **monotonic**: the video transfer fills only its share of the bar (`VIDEO_BYTE_WEIGHT` 0.85) and the audio transfer the rest, so the bar keeps rising when the second stream starts. It used to return the plain video fraction during the video phase and switch to the byte-weighted sum afterwards — with the audio at 0% that is 0.85, so the bar painted to 100% and then visibly jumped *back* to ~85% before climbing again. The 0.85 reservation is released by `mark_complete()` (`completed` flag) for a download that turned out to be a single muxed stream; `run_download()` therefore pushes the terminal `update_dock_progress` itself, since the last percent line only reaches the video's share.
- Audio-only and video-only downloads are single-stream and are not rescaled (`media_type` check returns the bare fraction).
- `setDockProgressOverlay()` repaints the tile (NSImage alloc + app-icon redraw + `-display()`) for every yt-dlp percent line, which is far more often than the eye can see. It is **throttled** by `should_redraw_dock(last_fraction, new_fraction)` — a pure helper in `ytdl/app.py` — against `DOCK_PROGRESS_MIN_DELTA` (0.005). Measured on a realistic 6000-line stream: ~207 repaints instead of 6006 (96% fewer).
- The throttle always repaints the 0.0 and 1.0 endpoints, so a download never appears to stall just short of full. `_last_dock_fraction` (init `-1.0`, "nothing drawn yet") holds the last **drawn** fraction, not the newest value, so each decision is measured against what is actually on screen. `clearDockProgress()` resets it to `-1.0` so the next download always paints a first frame.
- This is separate from the write-only `_last_progress_values` attribute, which is not read by anything.

## Cancellation
- `cancel_download()` is a main-thread method: it sets `_cancelled` and SIGTERMs the download's **process group**, so a running ffmpeg child dies with yt-dlp instead of being orphaned mid-merge. `run_download()` starts `Popen(..., start_new_session=True)` to make the group killable; `_terminate_process_tree()` falls back to `process.terminate()` if the group is already gone.
- It works by *killing the process*, not by adding a parallel cleanup path: the stdout loop ends on EOF, the process exits nonzero, and the **existing** `finally` block performs all UI cleanup (state, progress reset, label, button re-enable, dock). That is why there is no second finalizer to keep in sync.
- Two attributes carry all the state: `_proc` (the `Popen`, set by the worker and cleared in `finally` so no stale PID can be signalled later) and `_cancelled` (reset in `finally`, and set unconditionally so a Cancel landing in the few-ms window between thread start and `Popen` is honoured by the post-`Popen` check).
- A cancelled run reports "Download Cancelled" with **neutral** styling and clears the dock badge — it is not a failure, so it must not show the red "Download Error 🚨" state or a `!` badge.
- The Cancel button lives in the download row and is deliberately **absent from `_set_ui_enabled_state()`'s control list**, so it stays clickable while the rest of the UI is disabled. It is shown/hidden through `set_cancel_button_visible` — never touched directly from the worker's `finally`, because widget access is main-thread only. The show is the **last** thing `start_download()` does before spawning the thread, i.e. after every early return (no title, directory failure, "already downloaded" skip, invalid URL): showing it earlier leaves a live Cancel button with no download behind it.
- `cancel_download()` has **two** deliberate no-ops, both returning `False`: (1) no process yet — the intent is still recorded in `_cancelled` so `run_download()`'s post-`Popen` check terminates immediately; (2) the process has already exited (post-processing) — measured tail is ~0.1s (ffprobe 0.07s, subtitle resync 0.03–0.06s for a 3h file with 2 SponsorBlock segments), so this is rare, but honouring the click would relabel a *finished* download as "Cancelled" and zero its progress bars. In that second case `_cancelled` must stay `False` — returning `False` alone is not enough, since `run_download()`'s `finally` reads the flag back for its verdict. `Esc` is bound globally but only acts while `is_download_running` is true.
- `closeEvent()` sets `_shutting_down`, calls `cancel_download()`, then defers to `super().closeEvent(event)` so cancelling never swallows the close.
- **Teardown guard.** `self.signals` is a QObject owned by the window and is destroyed with it, so a worker still winding down after a close would emit into a dying object — which raises `wrapped C/C++ object ... has been deleted`, and at interpreter shutdown can take the process down with no traceback. Rather than a `join()` (that would freeze the main thread on every close) the worker emits through `DownloadMixin._emit(name, *args)`, which no-ops while `_shutting_down` is set. **Every worker-thread emit routes through `_emit`**: `run_download`, `_parse_download_output`, `_update_download_progress`, `_analyze_downloaded_file`, `get_file_metadata`, `create_nfo_file`, `create_edl_file`. Qt-free work — EDL/NFO, subtitle files, ffprobe, logging — is unaffected and still completes on close; only the UI notification is dropped, and nobody can see it once the window is gone.
- **Main-thread emits stay direct — do not "fix" them.** `_emit()` exists to guard the *worker* thread. `start_download()` and `cancel_download()` are main-thread-only (button click, `Esc`, `closeEvent`), so their `self.signals.*.emit(...)` calls are correct as written even though `closeEvent` has already set `_shutting_down` by the time it calls `cancel_download()`. Routing those through `_emit()` for consistency would silently swallow the "Cancelling download…" line on window close. `_emit()` is a worker-thread guard, not a universal emit wrapper.
- Covered by `temp/test_download_cancel.py` (synchronous, fake process: no threads/events/sleeps) plus `temp/test_download_completion.py` (cancelled-run, teardown-suppression and skip-path cases).

## Subtitle & progress parsing
- yt-dlp downloads subtitles BEFORE the media streams; their `[download] Destination:` and percent lines must not affect the video/audio progress bars or the captured media filename.
- Detection lives in `SUBTITLE_EXTENSIONS` + `YTDLPDownloaderGUI._is_subtitle_path()`; exclusion logic in `_parse_download_output()` / `_update_download_progress()` (state key `downloading_subtitles`).
- Retry re-prints: after a mid-download error ("Got error ... Retrying (n/10)...") yt-dlp RE-PRINTS the `[download] Destination:` of the SAME file. `DownloadProgressManager.on_download_destination(dest)` therefore dedupes by normalized destination path (`last_destination`, strips quotes/`.part`/`.ytdl`/`.temp`) so a retry does not advance the stream accounting video → audio. A captured example lives in `temp/retry-timeout-capture.log` (replay: `python3 temp/replay_ytdlp_output.py temp/retry-timeout-capture.log video`).
- Languages whose info fetch reports "(none)" availability get their checkbox disabled and unchecked in `_update_subtitle_checkboxes()`; the set `subtitle_unavailable` makes `_set_ui_enabled_state()` keep them disabled across UI re-enables (fetch/download start/end). After an info fetch the language checkboxes stay unchecked — selection is manual; `_update_subtitle_checkboxes()` only refreshes labels/availability, and a language the user checked survives a fetch unless it became "(none)". The single exception is "Subtitles only" mode (Video and Audio unchecked, Subtitles checked — which downloads nothing else): there the selection is auto-filled via `_auto_select_subtitles()` — "(real)" languages are checked, "(auto)" as fallback — both when the mode's Subtitles checkbox is selected and after a fetch in that mode.
- `video_state["available_subtitles"]` is reset to `{}` at the top of `get_video_info()`, before any yt-dlp call, and `update_subtitle_checkboxes` is emitted on **every** path (right before `title_fetch_complete`), not just the success path. Otherwise a failed fetch — nonzero exit, timeout, no audio, or a subtitle parse error — left the previous video's languages in the dict with their checkboxes still enabled, and `get_selected_subtitle_codes()` would then request subtitles the new video does not have. The key is deliberately *not* cleared by `on_url_text_change()`; the per-fetch reset covers every path, including a Reload on the same URL. The parse block's `except` is plain `Exception`: `json.JSONDecodeError` is unreachable there because `subs_dict`/`autos_dict` were already decoded from `json_data` at the top of the method.
- `video_state["description"]` is reset to `""` at the top of `get_video_info()`, next to the `available_subtitles` reset, for the same reason. It is written only on the success path (via `update_video_state`), but `_emit_description_summary()` reads it on **every** path — so a failed fetch (nonzero exit, timeout, invalid JSON, no audio, missing title) re-printed the PREVIOUS video's description in the output panel, and the stale text also leaked into the thumbnail dialog and the NFO `<plot>`. With the reset, a failed fetch shows no description instead of the last successful one. Covered by `temp/test_description_state_reset.py`.

## Subtitle display layout
- **The active stage is the paired-window layout: `ytdl/subtitle_layout.py::rolling_cues()`.** It reproduces the YouTube player's own look — two caption lines on screen at once, both shown whole instead of rolling in word by word. `ROLLING_WINDOWS_PER_CUE` (2) consecutive ASR windows become one cue, one window per line. `SubtitleMixin._format_subtitles_for_display()` calls it.
- **The ASR file already contains the display, and pairing is the whole change.** Each window is a short phrase, every window overlaps the next (100% of pairs, median 1.6s), and the downloaded file has **zero line breaks** (0 of 2398 cues across seven captures) — the two lines a viewer sees in the player are two *consecutive* windows, not one cue split in two. So the words are grouped in twos and nothing else is done to them:

      SET 1   the Peruvian skulls and              <- window 1
              No, before I thought Oh, go ahead.   <- window 2
      SET 2   Sorry.                               <- window 3
              No, go ahead.                        <- window 4

- **Nothing is repeated and nothing is re-cut.** Each window appears exactly once, on the line it occupies in the player — no carried/echoed line. The earlier draft repeated the finished window inside the next cue (because SRT cannot express two overlapping cues without the player stacking them); that was wrong for what was asked and is gone. `test_nothing_is_repeated` pins it.
- **Timing: the top line is anchored to the ASR's own clock.** A cue starts at its FIRST window's timestamp **verbatim** — not an interpolated word time, not delayed for reading speed — so it appears exactly when YouTube's would. It ends at the next set's first window, so cues never overlap and the display changes at an instant the ASR itself marks. The last set has no successor and keeps its own last window's end. There is no reading-speed model: durations are the ASR's own gaps, so a fast speaker gets short cues and a real pause stays blank — the same trade the player makes.
- **A window's text is written verbatim — never re-wrapped.** `rolling_cues()` does not split a long window, however wide it is: a long line stays a long line, exactly as YouTube shows it. A player that wants to fit it wraps it itself, and second-guessing that here would make the file differ from the captions for no gain. So a cue is *always* exactly one line per window (2 lines normally, 1 for an odd final window) — `test_exactly_one_line_per_window` pins it. Measured: the six English captures never exceed 40 chars per window; the German capture has 43 longer windows (worst 189 chars, because German words are longer) and those lines are simply left long.
- **Trade-offs inherent to copying the player:** cues can end mid-sentence (the ASR's lines are phrases, not sentences — this is what the sentence-aware stage used to fix, and it is the price of matching YouTube), and an odd window count leaves the final cue on one line.
- **The `>>` speaker marker is always stripped; bracketed sound cues are now optional.** Both happen in the parse step, before the layout: `^>>\s*` is removed unconditionally (an ASR artifact, never authored text), while `_strip_nonspoken_brackets()` is gated on the `strip_bracketed_soundcues` preference (default **true**, so behaviour is unchanged for existing installs). The preference is read **once per file**, so a save mid-run cannot produce a half-stripped file. With the strip off, a cue that is nothing but `[musik]` keeps its text and is no longer counted in the `no text` counter — correct, because the viewer sees it. The strip only ever runs on tracks that reach `resync_subtitles`: `real` (manual) subtitles bypass it by design, so they keep their brackets whatever the preference says.
- Covered by `temp/test_subtitle_rolling.py` (verbatim ASR starts, two windows per cue, no overlap, each window keeps its own line verbatim, nothing repeated, no word ever lost, plus the hand-checked edge cases) and `temp/test_subtitle_postprocessing.py` (the written file and the summary line).

- **The sentence-aware stage is gone, removed in 1.4.3.** It shipped as 1.4.0–1.4.1 and re-packed the word stream so cues ended at sentence ends (42–56% of cues at the 8-word default, vs the ASR's own boundaries), with durations from a reading-speed model (`LAYOUT_TARGET_WPS` 2.4, band 2.4–3.4). Once the paired-window layout took over nothing called it, so it went together with the `subtitle_words_per_cue` preference that drove it — roughly 330 lines of layout code, 35 of preference plumbing and 439 of tests that only exercised dead code. It is in git history if it is ever wanted back: `git show 349d0eb` is the last state that had it, and that is a better record than keeping the code alive as an "escape hatch".
- **The overlap guard still applies, and is still final.** `_fix_subtitle_time_overlaps()` returns `(cues, dropped)`. A cue that would overlap is first given room by trimming its neighbour's end (text untouched, no cascade); an out-of-order cue or one with no duration is *shifted* to where it fits. Deleting is the last resort, because a subtitle a fraction late is much better than a missing sentence. When a cue still cannot be placed, `_warn_about_dropped_cues()` names the file and the count in the panel (`⚠️`) and puts the text of each lost cue in the log. The rolling stage already produces a monotonic sequence (a cue ends where the next window opens), so this drops nothing in practice — it is there so a future change cannot write an overlapping or lossy file. `TestNoTextIsEverLost` asserts it per capture: the tripwire that makes a future silent loss loud. Do not "simplify" this back into a delete branch.
- **The `📊` line reports what the active stage did.** For the rolling layout that is `in → out · two-line` plus the parse/filter loss counters (`no text`, `too short`, `dropped`); `in == out` because the windows are kept. `wps` / `fast-paced` belonged to the removed sentence-aware reading-speed model and no longer appear.

## Tuning the layout
- **Tuning the paired-window layout means `ROLLING_WINDOWS_PER_CUE`**, the number of consecutive ASR windows per cue (2 = the player's look). It is a module constant, not a preference: 1 gives one line per cue, 3 gives three. Pass it per run as `rolling_cues(cues, windows_per_cue=n)` rather than editing the constant — the helpers take it as a default argument bound at import, so rebinding the module attribute at runtime silently does nothing.
- **The line width is deliberately not tunable**, because windows are never re-wrapped: a long line stays a long line, exactly as the captions have it.
- **Existing `.srt` files are never re-laid-out** — there is deliberately no re-layout feature, so any future knob would affect only newly processed subtitles.

## Subtitle file naming
- The processed subtitle is **always** written to a name the app chooses itself (`<title>.<lang>.srt`, or `<title>.srt` when it is the video's only subtitle), never to whatever name the site/yt-dlp produced — `_normalize_subtitle_names()` renames `<title>.en-auto.srt` / `<title>.deu.srt` / `<title>.a.en.srt` to the canonical name first, and `_resync_subtitle_for_language()` overwrites that single file in place. Both take the same `bare` flag, so the two can never disagree and leave a duplicate behind.
- **A single subtitle is stored without the language code**: `Title.srt`, not `Title.en.srt`. The rule is literal — `_uses_bare_subtitle_name(count)` is just `count == 1`, where `count` is the number of subtitle files that actually landed. How many languages the *site* offers is irrelevant: a request for `en`+`de` on a video that only delivers `en` still ends up as `Title.srt`. Two or more files keep their codes, because the code is then the only thing telling them apart.
- A bare name records no language, so a later run cannot read it back. `_bare_subtitle_credit(selected_langs)` decides what `Title.srt` / `Title.vtt` may count for in start_download()'s "already downloaded" pre-check: it is credited to **one** language, and only when the request covers *every* language the site offers (`available_subtitles ⊆ selected_langs`) — then the file has to be one of them. Crediting at most one keeps a multi-language request from being skipped (the others are still missing, so the run re-requests them and the folder ends up tagged again). It is credited to **nothing** when the offered languages are unknown (no info fetch) or when the site offers a language that was *not* requested — crediting it there would skip the download and silently leave the wrong language on disk. Without any credit, the subtitle is re-requested: correct, but the media file is re-downloaded with it, which is why the covered-set case exists.
- A bare file can only come from an earlier run that produced a single subtitle. If a later run produces two or more language-tagged files, `_remove_superseded_bare_subtitle()` deletes the leftover — the new files supersede it and its language is no longer recoverable from the name. It is only called when this run actually produced subtitle files, so a failed re-download never destroys the only copy.
- Progress parsing, the progress manager and `_is_subtitle_path()` are extension-based, so `<title>.srt` needs no special handling there; yt-dlp still writes its own `<lang>` name during the transfer — the rename is purely a post-processing step.
- Covered by `temp/test_subtitle_single_naming.py` (the literal one-file rule, the pre-check credit decision, path builder, normalize/resync, leftover removal, plus end-to-end `run_download()` runs with a fake process) and the `TestLanguageLessSubtitlePrecheck` cases in `temp/test_existing_subtitles.py`.

## Common gotchas
- GUI updates must use signals, not direct widget modifications.
- Signals emitted from **worker threads** are queued to the main thread and only delivered while the Qt event loop is running. Headless test harnesses (and replay scripts) have no event loop, so cross-thread emissions are silently dropped: call the emitting code from the main thread, or drive the helper directly (see `TestOdyseeInfoParse.test_wait_hints_emitted_while_waiting`, which runs `_info_wait_monitor()` while a timer thread sets its stop event).
- **Never call `QTimer.singleShot` from a plain `threading.Thread`** — a plain thread has no Qt event loop, so the timer is silently dropped by Qt 6 with no warning or exception. The correct pattern for handing work back to the main thread from a worker is to emit a queued signal (`pyqtSignal`); Qt delivers it to the main-thread slot automatically. `open_thumbnail_dialog` uses this pattern: the worker thread emits `signals.thumbnail_ready` (bytes), and the main-thread slot `_show_thumbnail_dialog` builds the dialog. The `QTimer.singleShot(0, scroll_to_bottom)` in `open_log_dialog` is fine — it is called from the main thread.
- Never bind the same key sequence to both a `QShortcut` and a menu `QAction` — Qt treats the duplicate as ambiguous and fires **neither** (silent failure). One binding per key; menu `QAction`s already work window-globally. Observed with `Ctrl+,`/Preferences (fixed).
- Avoid relative paths when invoking external binaries; rely on `find_binary()` (wraps `shutil.which()` and adds macOS/pip fallbacks).
- **Extraction errors on a specific video** are usually upstream breakage, not an app bug — try the nightly yt-dlp (`python3 -m pip install -U --pre "yt-dlp[default]"`), upgrading the copy `find_binary()` actually resolves. Full procedure incl. the PEP 668 and rollback variants: `setup.md` §6.
- **A browser saying a video is "not available" does not mean yt-dlp will fail** (ARD/ZDF geo/rights notices are a player-side check); observed live, such a video downloaded fine. Only a player API that returns no formats fails. See "Multi-site support".
- Do not modify `archive/` files – they are frozen snapshots.
